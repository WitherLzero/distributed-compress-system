## A. 最高优先级（阻塞设计文档）

| # | 问题 | 我们的当前理解 / 倾向 | 状态 |
|---|---|---|---|
| 1 | **"7 天无访问"的 xtime 从哪来？** | HDFS 默认 `dfs.namenode.accesstime.precision` 为 1 小时，且许多生产集群为性能**直接关闭 atime**。所以怀疑是：业务访问日志 / 独立 xtime 服务 / 自研 datanode 自带记录 | ✅ 第2课：就是**文件系统自带 atime**（XFS/ext4 等）；block 的元数据（内存中）含 block id + xtime，client 只读记录、不负责记录 |
| 2 | **压缩元信息存哪、什么格式？** | 记录原始长度、压缩后长度、单位、算法标记；倾向**与数据同址的文件头**，但 HDFS block 语义下如何落待定 | ✅ 第2课：**与数据同址的文件头**；按 1MB/4MB 分块，每块记原/压缩后 offset+len（约 4~6 字节/项）+ 算法枚举（~1 字节）；头部**预留 4KB 对齐** |
| 3 | **压缩后替换原数据的原子性与回滚？** | 压缩期间若有读请求怎么办？失败如何回滚？ | ✅ 第2课：先写**临时目录**，完成后靠**文件系统 rename 的原子性**替换；client 无需特殊处理；datanode 启动时须**扫描清理 temp 垃圾**（否则日积月累） |
| 4 | **server 被 kill 时正在压的任务如何处理？** | 倾向：完全无状态，客户端超时→退避→整个重做；牺牲少量重复计算换极简一致性 | ✅ 第2课：确认**直接杀死**（VM/容器）；client 靠**超时重试其他实例**；server 心跳丢失 → master 感知 → 剔除出分配 |
| 5 | **深压缩是叠加在浅压结果上，还是先解压再深压？** | 倾向后者更简单（元信息只需记录一层最终状态） | ✅ 第2课：原系统在**数据节点解压**后再发深压（当时带宽够+解压极快）；导师建议现代环境（36~100+ 盘位、带宽成瓶颈）**发往远端解压更好**——属策略取舍，两种都要在文档中写明 |

## B. 架构与运行

| # | 问题 | 我们的当前理解 / 倾向 | 状态 |
|---|---|---|---|
| 6 | **谁指示 scheduler 拉起 compress_server？** | 图上**没有** scheduler 与 master 的任何连线，所以存疑：master 申请 / 独立控制器 / 常驻服务作业 / 定时任务 | ✅ 第2课：master **不会主动申请**；调度系统按容量配额拉起/回收（资源不足就杀）；**本项目不写 scheduler**，用一个 Shell 脚本模拟（如每小时启动一个、半小时杀一个） |
| 7 | **原系统 datanode 是否为 C++ 自研？** | 图注写"（HDFS）"，但 **Java 的 DataNode 无法嵌入 C++ lib**，故推断原 datanode 是自研 C++，"HDFS"是类比 | ✅ 第2课：确认 client 以**动态库/静态库连编进 datanode**（即 datanode 为 C++ 自研）；server、master 为独立进程 |
| 8 | **存储集群与离线集群网络是否互通？** 带宽/延迟约束？ | 生产环境常物理隔离，而压缩数据是 GB 级大流量——跨机房带宽是否够？ | ✅ 第2课（背景性答复）：当年带宽够；如今盘位增多（36→70+甚至上百）、需上百 G 网卡，**带宽成为新瓶颈**——影响解压位置决策（见 #5） |
| 9 | **心跳间隔与判死超时阈值具体多少？** | 倾向超时取心跳间隔的 3~5 倍 | 🔵 **自决**（不上问）：心跳 5s、判死阈值 20s（×4）；落 §3.2，W4 联调可调 |
| 10 | **判死是主动扫描还是惰性过滤？** | 主动扫描便于输出监控指标；惰性最简 | 🔵 **自决**（不上问）：主动扫描（本地遍历，不发 RPC）+ 查询时过滤兜底，扫描周期 1~2s |
| 11 | **注册与首次心跳是合并还是分开？** | 倾向合并（注册即首次心跳） | 🔵 **自决**（不上问）：合并——启动立即发一次心跳即完成注册 |
| 12 | **master 的注册表是否需要持久化？重启后如何恢复？** | 倾向不持久化，重启后靠 server 重新注册自愈 | 🔶 部分答复：生产用 Raft 组（3 进程，注册表随主切换同步）；本项目按倾向（不持久化）执行 |

## C. 设计取舍

| # | 问题 | 我们的当前理解 / 倾向 | 状态 |
|---|---|---|---|
| 13 | **选 server 的决策者是谁？**（master 指定 / master 排序 / client 自选） | 倾向 **master 提供全局视图 + 推荐排序**，client 做最终 pick + 运行时重试 | ✅ 第2课：master 给**总表**，client **random 自选**；撞上队列满就**退避再选**。生产规模（几百上千台）下 random 最优 |
| 14 | **排序依据的 score 算法？** | 倾向**队列长度为主、CPU/MEM 为辅** | ✅ 第2课：生产就用 **random**（"集群够大，所有算法干不过 random"）；但 server 心跳仍上报**队列长度/CPU/内存**，为将来策略演进保留 |
| 15 | **压缩方案是否考虑 Zstd？** | 导师方案是 LZ4 + LZMA 两个极端；Zstd 单库多档位是现代替代。是否要作为备选写入设计文档？ | ✅ 第2课：原系统从 LZMA 向 Zstd 部分迁移（未全切，LZMA 压缩率仍最优，文本可 ~10x）；业界（RocksDB 等）主流是 **LZ4 + Zstd**。方案可写 LZ4+LZMA，提及 Zstd 演进；**面试需能报各算法速度/压缩率**（LZ4 ~GB/s，LZMA ~1MB/s，Zstd 高档 ~3.0） |
| 16 | **mock 的粒度是否合适？** | 只 mock 到"能触发我们自己逻辑"的程度（见 `docs/adr/0001`） | ✅ 第2课：认可——写一个**只扫目录、投喂数据的假 datanode**（验证 client 动态库形态）+ 本地造 64MB 文件；**不写 scheduler**（脚本代替） |
| 17 | **master 是否需要 HA？** | 倾向本期不做（单机演示环境），但想知道真实系统怎么做 | ✅ 第2课：生产是 **Raft 选主**（3 进程，1 主 2 备，主挂自动切换，状态同步；另有 DNS/文件锁等轻量方案）；**本项目不实现**，但建议学习 Raft 原理 → ADR-0002 依据成立 |

## E. 依赖库 / RPC 相关

| # | 问题 | 我们的当前理解 / 倾向 | 状态 |
|---|---|---|---|
| 21 | **原系统如何处理大文件？有没有分片？** | BRPC 默认单消息上限 **64 MB**，而我们数据动辄 GB 级。倾向**分片**（顺带解决重试粒度），但想知道原系统做法 | ✅ 第2课：确认**分块压缩**（64MB 数据按 1MB/4MB 一块），元信息逐块记录 offset+len |
| 22 | **压缩后数据由谁写回存储？存储端有无版本机制？** | 我们推断**写回是 client 做的**。若确实如此，需要**版本号/CAS** 防 lost update | 🔵 已并入 #3（第2课答复：client 调 rename 原子替换）；存储端版本机制未提及 → 自决保留 §5.2 的版本号机制约束 |
| 23 | **RPC 超时怎么定？** | BRPC 默认 **500 ms**，而 LZMA 压 100 MB 需 ~100 秒 → 必然重试风暴。倾向按 `数据量÷带宽 + 数据量÷压缩速度 + 排队` 动态估算 | 🔵 **自决**（不上问）：动态公式已写入 §5.6，数值 W4 联调实测 |
| 24 | **压缩任务的幂等性如何保证？**（重试导致重复压缩） | 倾向用**版本号（乐观并发）** | ✖ 已删除（不上问）：被 §5.3（压缩 RPC 无副作用、重试安全）覆盖 |
| **25** | **BRPC 官方不支持 Windows，本地用什么环境编译？**（WSL2 / Docker / 云主机 / 只出设计不出二进制） | 已确认 vcpkg 的 brpc port 标注 `"supports": "!android & !windows"`；官方支持列表只有 Linux / macOS（WSL 归 Linux）。BRPC 的 IO 依赖 epoll/EDISP 等 Linux 设施。而我的环境是 **Windows + MSYS2(UCRT64)**，这直接影响 W3「打通编译流程」交付物 | ✅ 第2课：**WSL2 可行**（brpc 支持 Linux 环境）；本项目服务跑物理机即可，不碰 Docker |
| **26** | **原系统的离线集群调度器是 YARN 还是 K8s？** datanode 是裸金属还是容器？ | 这决定 `compress_server` 的真实部署形态（K8s → 无状态 Pod；YARN → 裸金属/容器进程），也决定 `mock_scheduler` 该模拟哪种调度语义。行业现状：计算层在迁 K8s，存储层仍以裸金属为主（详见 `docs/research/external-systems.md` §4.4） | ✅ 第2课：那个年代是**自研类 Docker 容器**（尚无 Docker/K8s）；如今业务系统普遍 K8s（底层仍容器）；**存储系统不用容器**（数据安全敏感+虚拟化损耗）。本项目跑物理机 |
| **27** | **BRPC 的 `leveldb` / `openssl` 依赖能否裁掉？** | 二者均为可选：leveldb 仅 rpcz、openssl 仅 https。本期不用 | 🔵 **自决**（不上问）：本期不用，构建时禁用 |
