## A. client 对外 C++ 接口形态 ✅ 已定稿（2026-11-07）

**背景**：导师否决 C ABI（01:05:31–01:07:39），方向已定回 C++（ADR-0005）。2026-11-07 讨论定稿，**采纳选项 1（函数式 C++ API + 错误码）**，四个子问题结论：

1. **错误处理**：`enum class CompressErr`（包 §5.5 框架 + 移植 C ABI 七个返回码），接口 `noexcept`，库内异常在边界统一 catch 转错误码——ADR-0003 时代「异常不得穿越边界」的纪律保留，理由从「ABI」改为「一个 bug 不应杀死宿主进程」；
2. **配置传入**：`Options` struct 注入，**库内禁止 `DEFINE_*`（gflags）**——gflags 注册表是进程级全局且无命名空间，库在 dlopen 时注册与宿主冲突即 abort；且库 flag 只能经宿主命令行传，隐式耦合宿主启动契约。gflags 仅用于带 main() 的二进制（master/server/mock_datanode）；
3. **形态**：`namespace compress::client`（target 同名）；工厂 `Status Create(const Options&, std::unique_ptr<Client>* out)`（无异常出口）；`class Client` Pimpl，`Start()/Shutdown()` 幂等、析构 RAII 兜底；`Version()` 校验兼容；
4. **`Read` 语义**：对齐 POSIX `pread`——同步阻塞、调用方出 buffer、缓冲不足时 `*out_len` 带回所需容量（`kBufSmall`，原 `CCL_EBUFSMALL`）、可多线程并发。

定稿细节落 [ADR-0005](../../docs/adr/0005-client-interface-cpp.md)「已定接口形态」节；设计文档 §6.2 重写随 B/C/D 全部定稿后一次落（见本 issue Acceptance）。

**被否决项**：类 + 异常（与"server 随时被杀、错误码驱动退避"的系统调性不一致；接口边界异常安全成本高）。

## B. 压缩率阈值与"放弃压缩"的落盘规则 ✅ 已定稿（2026-11-07）

**背景**：导师（53:58–55:18，由 §5.2 异常表「数据不可压缩…按未压缩状态存储」一句含糊表述引出）：按整体压缩率决策，"低于百分之多少就不压，不浪费 CPU"；整块要么全压要么不压（"既混着压又混着不压，生产环境特别容易出问题"）。

**结论**：**采纳选项 1（节省率阈值 + 放弃即不动原文件）**，子问题定稿：

1. **决策单位 = DataNode 上的块文件，不是用户文件本身**。文件本就按块分布存储，单个 DataNode 只见自己的块；"整个文件的压缩率"概念不存在。块内部按 4MB 切片传输/压缩（§6.1.4），但放弃决策只在收齐全部切片后按整块节省率做一次，粒度不细到切片；
2. **阈值不钉死数值**：描述为"由生产环境与实际情况配置"，初始值占位 **10%**（压缩后仍 ≥90% 原始大小即放弃），可配；
3. **深压（LZMA）与浅压同一条阈值**：规则统一易解释；若实测数据证明需区分，后续以新增配置项演进，不改决策机制。

**落盘语义**：节省率 ≥ 阈值 → 写「文件头 + 切片条目 + 压后数据」temp 文件 → rename 原子替换原块文件；< 阈值 → 丢弃全部压缩产物，**原块文件不动、不写任何文件头**（无头即"未压缩"，读取路径天然兼容）。

**被否决项**：选项 2（写"未压缩标记"文件头）——增加一种磁盘状态，导师反对混合存储语义。

## C. 压缩中途被读的取消机制 ✅ 已定稿（2026-11-07）

**背景**：导师（30:54）：压缩到一半 block 被前台读取应取消任务；垃圾数据清掉。检测机制未讨论。

**结论**：**采纳「内存版本号」机制**（学员提出的"文件头带版本号"方案经修正后采纳）：

1. **版本号不存磁盘文件头**——压缩进行中原块无头（头只在成功后写入），版本号活在 client 内存的 block → version 映射（`BlockMetaView`）；
2. **Read 命中块即 version+1**（与 atime 刷新同一时机）：atime 管「下轮扫描不再选中」= 被动防重选，版本号管「在途任务立刻止损」= 主动取消，读一次两个效果同时发生；
3. **压缩线程每收齐一个切片比对一次版本号**（64MB 块 = 16 个止损点）：变化 → 终止任务、丢弃全部已收切片、删除 temp、记日志；server 无状态不参与取消，client 停发后续切片即可；
4. **全部收齐后、回写前二次校验**版本号，通过才 rename；
5. 同一机制顺带覆盖块被删除场景（导师只点了被读，此为免费赠品）；
6. 机制定死，实现细节归 W5 集成阶段。

**被否决项**：版本号放磁盘文件头（压缩中原块无头，无处可放）；只在 RPC 返回时校验一次（最坏白压整块 64MB，LZMA 数分钟）；扫描线程维护「在读集合」（版本号是其等价轻量实现）。

## D. 文件头 4K 布局字段表 ✅ 已定稿（2026-11-07）

**背景**：导师（01:08:34–01:09:32）：「应该是总共 4K…包括这个 block meta 加起来总共 4K，而不是说一个文件头就 4K，这样太废了。你可以再算算，比方说你假设 64 兆，那 4 兆压一次，或者是 1 兆压一次，你这个东西怎么布局？」——4KB 是头+条目合计预算（单头 4KB 太费）；整个文件单算法字段；留算术作业。

**结论**：

1. **单位与形态**：文件头每**块**一个（用户文件按块分布，192MB 文件 = 3 块 = 3 个独立文件头）；自包含于压缩后块文件开头的一段字节，不建独立元数据文件；未压缩块无头（无头即未压缩，读路径天然判据）；
2. **布局**（`#pragma pack` 手工钉死，不用 protobuf）：定长头 128B = magic `"CPS1"`(4) + version(2) + algorithm(1) + flags(1) + slice_count(4) + origin_block_size(8) + reserved(108)；切片条目 8B/条 = compressed_len(4) + crc32(4)；`origin_offset`（= 序号 × slice_size）与 `compressed_offset`（前缀和）可推导不存；条目集中头区、不与数据交错；
3. **预算核算**：4KB 可装 496 条；64MB 块 @4MB 切片 = 16 条 = 合计 256B，余量 16 倍；预算对切片给下限 ≥132KB（块变大同比上移），4MB 切片可支撑块至约 2GB；
4. **切片大小 v1 钉死 4MB**：页预算 + LZ4 窗口定下限，前台读路径三代价（解压延迟 / 内存峰值 / 重试取消粒度）定上限——切片变大不威胁预算（条目变少）但恶化前台，系统调性前台读优先故取偏小端；LZ4 frame 格式块上限即 4MB；格式演进走 `version` 字段；
5. **crc32 必选**：RPC 无校验和，网络抖可 silent corruption；校验成本不足压缩时间 1%；与「rename 前整文件读回校验」配合可逐切片定位损坏；
6. **命名**：磁盘条目定名 `SliceEntry`（原 `BlockMeta` 与上级「块」撞词）；`CompressedFileHeader` 保留。

**被否决项**：条目与切片数据交错（读第 k 片须顺序扫前 k 头，且一页预算只在集中时成立）；独立元数据文件（rename 原子性要管两个文件）；变长切片保留 `origin_offset`（定长切片可推导，不付这 8B）；protobuf 头（手工钉死定长布局）。
