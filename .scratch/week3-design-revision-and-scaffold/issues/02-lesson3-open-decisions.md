## A. client 对外 C++ 接口形态 ✅ 已定稿（2026-11-07）

**背景**：导师否决 C ABI（01:05:31–01:07:39），方向已定回 C++（ADR-0005）。2026-11-07 讨论定稿，**采纳选项 1（函数式 C++ API + 错误码）**，四个子问题结论：

1. **错误处理**：`enum class CompressErr`（包 §5.5 框架 + 移植 C ABI 七个返回码），接口 `noexcept`，库内异常在边界统一 catch 转错误码——ADR-0003 时代「异常不得穿越边界」的纪律保留，理由从「ABI」改为「一个 bug 不应杀死宿主进程」；
2. **配置传入**：`Options` struct 注入，**库内禁止 `DEFINE_*`（gflags）**——gflags 注册表是进程级全局且无命名空间，库在 dlopen 时注册与宿主冲突即 abort；且库 flag 只能经宿主命令行传，隐式耦合宿主启动契约。gflags 仅用于带 main() 的二进制（master/server/mock_datanode）；
3. **形态**：`namespace compress::client`（target 同名）；工厂 `Status Create(const Options&, std::unique_ptr<Client>* out)`（无异常出口）；`class Client` Pimpl，`Start()/Shutdown()` 幂等、析构 RAII 兜底；`Version()` 校验兼容；
4. **`Read` 语义**：对齐 POSIX `pread`——同步阻塞、调用方出 buffer、缓冲不足时 `*out_len` 带回所需容量（`kBufSmall`，原 `CCL_EBUFSMALL`）、可多线程并发。

定稿细节落 [ADR-0005](../../docs/adr/0005-client-interface-cpp.md)「已定接口形态」节；设计文档 §6.2 重写随 B/C/D 全部定稿后一次落（见本 issue Acceptance）。

**被否决项**：类 + 异常（与"server 随时被杀、错误码驱动退避"的系统调性不一致；接口边界异常安全成本高）。

## B. 压缩率阈值与"放弃压缩"的落盘规则 ✅ 已定稿（2026-11-07）

**背景**：导师（53:58–55:18，由 §5.2 异常表「数据不可压缩…按未压缩状态存储」一句含糊表述引出）：按整体压缩率决策，"低于百分之多少就不压，不浪费 CPU"；整块要么全压要么不压（"既混着压又混着不压，生产环境特别容易出问题"）。

**结论**：**采纳选项 1（节省率阈值 + 放弃即不动原文件）**，子问题定稿：

1. **决策单位 = DataNode 上的块文件，不是用户文件本身**。文件本就按块分布存储，单个 DataNode 只见自己的块；"整个文件的压缩率"概念不存在。块内部按 4MB 切片传输/压缩（§6.1.4），但放弃决策只在收齐全部切片后按整块节省率做一次，粒度不细到切片；
2. **阈值不钉死数值**：描述为"由生产环境与实际情况配置"，初始值占位 **10%**（压缩后仍 ≥90% 原始大小即放弃），可配；
3. **深压（LZMA）与浅压同一条阈值**：规则统一易解释；若实测数据证明需区分，后续以新增配置项演进，不改决策机制。

**落盘语义**：节省率 ≥ 阈值 → 写「文件头 + 切片条目 + 压后数据」temp 文件 → rename 原子替换原块文件；< 阈值 → 丢弃全部压缩产物，**原块文件不动、不写任何文件头**（无头即"未压缩"，读取路径天然兼容）。

**被否决项**：选项 2（写"未压缩标记"文件头）——增加一种磁盘状态，导师反对混合存储语义。

## C. 压缩中途被读的取消机制

**背景**：导师（30:54）：压缩到一半 block 被前台读取应取消任务；垃圾数据清掉。检测机制未讨论。

**选项**：

1. **块级版本号 + 回写前二次校验（agent 提案）**：读取路径（`ClientCore::Read`）与扫描线程同进程，维护 block → 版本号映射；压缩循环每完成一块比对版本号（变了即中途被读 → 终止）；任务完成、回写前再二次校验 atime/版本号兜底。取消 = 丢弃 temp 文件。
2. 仅回写前二次校验：最简，但已浪费整段压缩 CPU（深压 LZMA 代价大）。
3. 扫描线程维护"在读集合"：读取时登记、读毕注销，压缩任务查集合。多一套同步状态，版本号是它的等价轻量实现。

**遗留子问题**：版本号映射的内存结构（与 data node 内存模型的对接方式）；压缩工作线程的取消点粒度。

➡️ agent 推荐选项 1（具体实现归 W5，本期只定机制与文档表述）。

## D. 文件头 4K 布局字段表

**背景**：导师（01:08:34–01:09:32）：文件头 + block meta **合计 4KB 上限**（不是一个头就 4K）；整个文件统一一个算法字段（1 字节甚至几位）；不能每块存算法。按 64MB / 4MB 分块重算布局。阻塞 issue 03 的文件头结构体。

**agent 布局提案**（待确认）：

- **定长 4MB 块**：64MB 文件 = 16 块。
- 头固定区（提案 128B）：`magic(4) + version(2) + algorithm(1) + flags(1) + block_count(4) + origin_file_size(8) + reserved(108)`。
- 块条目 8B/条 × 16 = 128B：`compressed_len(4) + crc32(4)`。
  - 可推导字段全部删除：`origin_offset`（= 块号 × 4MB）、`compressed_offset`（顺序存储前缀和）、`origin_len`（最后一块由 `origin_file_size` 推导）。
- **合计 ≈ 256B，4KB 为预留上限**（"不超 4KB"，不用满）；布局在头 `reserved` 区记录实际头长。
- crc32 配合「rename 前整文件读回校验」（issue 01 #8），每块校验比整文件校验定位更准。

**遗留子问题**：是否钉死"定长 4MB 块"（变长块需保留 `origin_offset`，条目涨到 12~16B，16 块也就 256B，仍在预算内——是否保留变长扩展性待讨论）；crc32 是否必选。

➡️ agent 推荐：钉死定长 4MB 块 + crc32 必选（数据安全性是导师主动提的需求）。
