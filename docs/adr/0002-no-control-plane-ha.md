# ADR-0002: 控制面不实现主备高可用

- **Status**: Proposed（待与导师确认）
- **Date**: 2026-10-19
- **Deciders**: 林昕祺（学员）、shanks（导师，待确认）
- **相关**: `issues/05` #17、设计文档 §3.2

## Context

`compress_master` 承担控制面职责：维护 `compress_server` 的注册表（实例地址、负载指标、最后心跳时间），并向 `compress_client` 提供可用实例列表。

这使 `compress_master` 成为一个**单点（Single Point of Failure）**：其不可用期间，`compress_client` 无法获取最新实例信息，新增压缩任务将受影响。

实现主备高可用需要引入以下机制，且每一项都不简单：

| 机制 | 问题 |
|---|---|
| 故障检测 | 备节点需判断主节点是否失效。网络抖动可能导致误判 |
| 选主 | 通常需引入第三方协调组件（ZooKeeper / etcd）投票选主 |
| 状态同步 | 主节点接收的每次心跳均需同步至备节点，同步过程本身可能失败或延迟 |
| 脑裂防护 | 误判会导致两个节点同时认为自己是主，状态分裂 |
| 客户端切换感知 | 客户端需感知主节点地址变化 |

## Decision

**本期不实现控制面主备高可用。**

`compress_master` 以单实例部署，接受其作为单点带来的可用性风险。

该风险由设计文档 §3.2.4 中的**降级行为**承接：控制面不可用期间，客户端使用本地缓存的实例列表继续处理已识别任务，缓存过期后暂停新增压缩任务，待 master 恢复后由下一次同步自动恢复。

## Rationale

1. **成本与收益不匹配**：上述五项机制的实施成本可能超过压缩服务本体。本项目为 6 周实习项目，资源应集中于核心功能的完整实现与联调。
2. **取舍性质明确**：这是基于时间与精力约束的范围取舍，**并非外部技术限制**。原系统是否实现控制面高可用尚待确认。
3. **风险已有承接方案**：单点风险并不意味着故障时系统直接失效。降级行为保证了故障期间系统有序退化，而非崩溃。
4. **可后续演进**：若将来需要提升控制面可用性，优先考虑的轻量方案是**注册信息持久化**——它规避了选主与脑裂问题，仅减少重启后的恢复成本，可独立于高可用方案实施。

## Consequences

**正面**
- 项目范围可控，资源集中于核心链路。
- 避免了选主、状态同步等分布式协调复杂度。

**负面 / 代价**
- `compress_master` 故障期间，新增压缩任务暂停；缓存未过期时仍可继续处理已识别任务。
- master 重启后若无持久化，注册表需依赖各实例下一次心跳重新构建。
