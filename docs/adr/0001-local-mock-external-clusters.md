# ADR-0001: 本地以 mock 替代真实外部集群

- **Status**: Accepted（第 2 课导师确认 mock 粒度与 datanode 形态）
- **Date**: 2026-10-19
- **Deciders**: 林昕祺（学员）、shanks（导师）

## Context

本系统是插在**既有**存储集群（类 HDFS）与**既有**离线计算集群（MapReduce / Spark）之间的压缩服务。它依赖的运行时环境包括：

1. **存储集群** —— 提供"读数据 / 写回数据"的能力，`compress_client` 以动态库形式嵌入其 datanode。
2. **离线计算集群** —— `compress_server` 运行其上，借用闲时算力。
3. **调度器**（YARN / K8s / 自研） —— 决定 `compress_server` 何时被拉起、何时被杀死。

开发期遇到的现实约束：

- 本地**不可能**部署一套真实的 HDFS + Spark/YARN 集群（资源、复杂度、时间都不允许）。
- 更关键的是：**真实 HDFS 的 DataNode 是 Java 进程，无法把 C++ 动态库链入其中**（除非为 JNI 桥接另做一套工程）。因此即使装上真 HDFS，也复现不了"client 作为 lib 嵌入 datanode"这一核心形态。

## Decision

在本地开发与演示环境中，**自己实现一组极简的 mock 组件**来替代真实外部集群，而不复用真实系统的实现：

| mock 组件 | 替代 | 只需实现 |
|---|---|---|
| **mock_storage** | HDFS 文件系统 | 本地目录模拟读/写/列文件，带大小与"最后访问时间" |
| **mock_datanode** | DataNode 进程 | 一个 C++ 宿主程序，加载 `compress_client` 库，暴露"扫描/读/写"桩 |
| **mock_scheduler** | YARN / K8s | 按指令**拉起/杀掉** server 进程，能模拟忙闲，能在指定时刻 kill（测重试） |

**mock 的尺度原则**：

> **mock 只需真实到"能触发我们自己的逻辑"，其余全部造假。**

明确**不做**：HDFS 的副本机制 / NameNode 元数据 / 容错 / 多节点；YARN 的资源计量 / 队列 / 公平调度 / 优先级。

注：`compress_server` **不是** mock 对象——它就是本项目要实现的真实模块，只是其"运行环境"（被谁拉起、何时被杀）由 mock_scheduler 模拟。

## Rationale

- **唯一的可行路径**：真集群无法在本地复现，且 C++ lib 无法嵌入 Java datanode。
- **成本收益**：mock 代码量远小于三个主模块，却能支撑 W4 / W5 的端到端联调；若不做，W4/W5 将无环境可测。
- **可控性**：mock 能按指令精确制造边界场景（server 正好在压缩中被 kill、队列打满触发反压），真实集群反而难以制造这些场景。
- **教学价值**：mock 迫使我们必须明确"到底依赖外部系统的哪些能力"，这个梳理本身就澄清了系统边界。

## Consequences

**正面**
- W3 即可完成 mock 层，为 W4/W5 留出充足的联调时间。
- 边界测试可控、可重复。

**负面 / 代价**
- mock 与真实集群存在行为差异（如真实网络的抖动、跨机房延迟），**本地跑通不等于生产可用**——这一点必须写进设计文档的"可靠性设计"作为已知局限。
- 多了一层需要维护的测试代码。

## 待确认（已于第 2 课闭环，2026-10-27）

- [x] 导师那套原系统的 datanode 是否为 **C++ 自研**？—— **是**。导师确认 client 以动态库/静态库**连编进 datanode**（Java DataNode 无法嵌入 C++ lib），"（HDFS）"为类比说明。
- [x] mock 的粒度是否合适——**认可**。假 datanode 只需"扫目录 + 投喂数据"验证 client 动态库形态；调度模拟**用 Shell 脚本**（定时拉起/杀 server），不写 scheduler（issues/05 #6、#16）。
