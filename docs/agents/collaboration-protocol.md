# 人机协作节奏约定：票 → 检查点 → 四拍循环

> 本文件是**持续生效的协作约定**（人机共同遵守），不是一次性决策。
> 双副本/环境/git 纪律见 `dev-workflow.md`；issue 粒度哲学见
> `issue-tracker.md`。本文件回答："一张实现票到手后，人与 agent 怎么配合，
> 学员以什么细度参与学习"。

## 1. 总模型

```
spec（issue 03 级，已讨论到验收线）
   │  /to-tickets
   ▼
工票（04-09 级：做什么 + 验收 checklist，无实现细节）
   │  每张票切成 2~3 个「检查点」
   ▼
检查点 = 一个可验证的小故事：仓库处于"能构建/能跑、一段话讲得清"的状态
   │  每个检查点走四拍循环
   ▼
commit → 下一检查点 → 票关闭
```

## 2. 检查点切法（粒度判据）

- **不按 acceptance 条数机械切**（条目间有依赖，"编译通过"是前面条目的结果而非并列一步）。
- 按"**这个状态学员能否亲手验证、agent 能否用一段话讲清**"切。
- 每个检查点一个 commit（代码在 WSL 侧，走功能分支；文档直接 main，见 `dev-workflow.md` §3）。
- **commit 与文档勾选同步**：每次提交检查点时，同步在对应 issue 里勾选/标注已完成的条目，让票的 checklist 永远反映仓库真实进度（2026-11-08 起）。

## 3. 四拍循环（每个检查点一轮）

| 拍 | 谁 | 做什么 | 耗时参考 |
|---|---|---|---|
| 预告/导读 | agent | 给导读：本 commit 动了哪些文件、每个文件一句话职责、指出一个值得看的设计决策点 | 学员读 5 分钟 |
| 亲手验证 | 学员 | 在 WSL 侧亲手构建/运行/跑测试（agent 不给"已验证"的结论，只给命令） | 5–10 分钟 |
| 审 diff + 提问 | 学员 | 自己看 diff；问 1–3 个问题（**不攒问题**——下一检查点的导读建立在当前认知上） | 10 分钟 |
| 答疑并开工 | agent | 答疑问，然后开工下一检查点 | — |

## 4. 学习细度与范围（三层）

| 层 | 学员掌握目标 | 不追什么 |
|---|---|---|
| **决策层**（必学） | diff 里每个文件为什么存在、接口为什么这样开、纪律为什么这样定（如压缩 buffer 2×、库内禁止全局配置注册、ADR-0003 单点替换） | — |
| **结构层**（应学） | 类之间依赖方向、include 图、构建组织——能讲清"这段代码挂在系统哪一层" | 逐行语法 |
| **语法层**（查即可） | 遇到不懂的写法当场问，agent 现场讲 | 预先系统性学语法 |

定位：面试考察"能否讲清自己仓库里每个决策为什么这么做"。写代码的手是 agent 的，
但 diff 的阅读权、构建的运行权、验收的判定权是学员的。后续想上手写代码时，
从 gtest 单测这类纯逻辑小件开始接管（issue 06/07 是天然入口）。

## 5. 边界

- 协议用于**实现票**（03 及以后）；修订/决策类 issue（01/02 型）仍走"讨论→落稿→终审"节奏。
- 票的验收 checklist 由学员终审后勾票关闭；agent 不自封票。
- 本协议 2026-11-08 起生效，随执行反馈修订（修订入口：直接改本文 + commit）。
