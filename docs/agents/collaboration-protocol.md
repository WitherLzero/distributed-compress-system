# 人机协作节奏约定：票 → 检查点 → 四拍循环

> 本文件是**持续生效的协作约定**（人机共同遵守），不是一次性决策。
> 双副本/环境/git 纪律见 `dev-workflow.md`；issue 粒度哲学见
> `issue-tracker.md`。本文件回答："一张实现票到手后，人与 agent 怎么配合，
> 学员以什么细度参与学习"。

## 1. 总模型

```
spec（issue 03 级，已讨论到验收线）
   │  /to-tickets
   ▼
工票（04-09 级：做什么 + 验收 checklist，无实现细节）
   │  每张票切成 2~3 个「检查点」
   ▼
检查点 = 一个可验证的小故事：仓库处于"能构建/能跑、一段话讲得清"的状态
   │  每个检查点走四拍循环
   ▼
commit → 下一检查点 → 票关闭
```

## 2. 检查点切法（粒度判据）

- **不按 acceptance 条数机械切**（条目间有依赖，"编译通过"是前面条目的结果而非并列一步）。
- 按"**这个状态学员能否亲手验证、agent 能否用一段话讲清**"切。
- 每个检查点一个 commit（代码在 WSL 侧，走功能分支；文档直接 main，见 `dev-workflow.md` §3）。
- **commit 与文档勾选同步**：每次提交检查点时，同步在对应 issue 里勾选/标注已完成的条目，
  让票的 checklist 永远反映仓库真实进度（2026-11-08 起）。

## 3. 四拍循环（每个检查点一轮）

| 拍 | 谁 | 做什么 | 耗时参考 |
|---|---|---|---|
| 预告/导读 | agent | 给导读：本 commit 动了哪些文件、每个文件一句话职责、指出一个值得看的设计决策点 | 学员读 5 分钟 |
| 亲手验证 | 学员 | 在 WSL 侧亲手构建/运行/跑测试（agent 不给"已验证"的结论，只给命令） | 5–10 分钟 |
| 审 diff + 提问 | 学员 | 自己看 diff；问 1–3 个问题（**不攒问题**——下一检查点的导读建立在当前认知上） | 10 分钟 |
| 答疑并开工 | agent | 答疑问，然后开工下一检查点 | — |

## 4. 学习细度与范围（三层）

| 层 | 学员掌握目标 | 不追什么 |
|---|---|---|
| **决策层**（必学） | diff 里每个文件为什么存在、接口为什么这样开、纪律为什么这样定（如压缩 buffer 2×、库内禁止全局配置注册、ADR-0003 单点替换） | — |
| **结构层**（应学） | 类之间依赖方向、include 图、构建组织——能讲清"这段代码挂在系统哪一层" | 逐行语法 |
| **语法层**（查即可） | 遇到不懂的写法当场问，agent 现场讲 | 预先系统性学语法 |

定位：面试考察"能否讲清自己仓库里每个决策为什么这么做"。写代码的手是 agent 的，
但 diff 的阅读权、构建的运行权、验收的判定权是学员的。后续想上手写代码时，
从 gtest 单测这类纯逻辑小件开始接管（issue 06/07 是天然入口）。

## 5. 学习笔记（知识库）机制

面试向个人复习库，2026-11-08 起随协作沉淀。

- **位置**：`local/kb/`（`local/` 已被 .gitignore 覆盖，不进 git、只在 Windows 侧，
  可用 Obsidian 打开成库）。
- **原子卡**：一张卡只讲一个概念；一张 MOC 索引卡分组挂载（backlink 自动成网，
  卡内不写关联节）。
- **卡片模板（v3，2026-11-08 定型）**：
  1. **是什么**——1~2 句；
  2. **怎么运作**——机制因果链：编号步骤、短句、约束须标注「从哪步推出」；
     排版纪律：禁整段密文、大概念分子标题；
  3. **实战锚点**——本项目 diff/文件里可亲手验证的落点；
  4. **面试话术**——30 秒内能讲出口的版本。
- **采集节奏**（挂检查点收口，不中断四拍循环）：agent 在检查点汇报时给出
  「本轮可沉淀清单」→ 学员勾选 → agent 按模板起草 → **学员改写**后定稿。
  学员当场追问深的知识点（如 volatile 汇编实证），答完即问是否落卡。

## 6. 边界

- 协议用于**实现票**（03 及以后）；修订/决策类 issue（01/02 型）仍走"讨论→落稿→终审"节奏。
- 票的验收 checklist 由学员终审后勾票关闭；agent 不自封票。
- 本协议 2026-11-08 起生效，随执行反馈修订（修订入口：直接改本文 + commit）。

## 7. 设计挑战机制（2026-11-16 起）

> 四拍循环与评审的**伴生件**，不改变四拍本身。由来：第 4 课（2026-11-14）复盘发现，
> agent 双轴评审（Standards/Spec）对「设计选择本身的合理性」系统性失明——设计与实现完全自洽
> 时，设计本身也可能次优（例：切片条目存压缩长度 vs 存压缩后 offset，随机读场景后者才对）。
> 导师以「为什么这么设计」口头补位的这部分，由此制度化。

### 7.1 触发与产出

每次检查点汇报（第一拍）与 PR 评审，agent 除缺陷清单外附**最多 5 条设计挑战**：只挑「有真实
取舍、且答案会影响后续代码」的点（API 形状、调用契约、资源生命周期、规模成本）；风格类琐碎
不进（那是 formatter 的事）。行业参照锚点来自 review 的 Industry 轴（code-review skill 第三
轴，评审时从本仓库依赖/先例/风格配置推导），不凭空断言。

### 7.2 挑战条目格式

- **[Challenge-N] 主题**：X 用 A 而非 B；
- **行业/系统参照**：（Industry 轴锚点或导师反馈出处）；
- **本仓选择**：；
- **质疑**：为什么不是 B？取舍点在哪？；
- **去向**：一个可直接抛给主 agent 的问题。

### 7.3 答疑分流（责任链）

学员先自答；答不上来**问主 agent 要解释**（补个人聚焦视角不全的缺口）；仍有疑义的带去导师
课。反向同样成立：导师反馈走「采纳 / 澄清 / 保留」三分法，保留项须能说明理由（实例：out_cap
是防越界容量契约，保留；TryPush 因 deque 分配可抛而刻意不标 noexcept）。

### 7.4 闭环归档

- 挑战答案落进 repo 既有的**理由载体**：票尾台账 / ADR / 头注释——理由在案后，同一点下次
  评审自动视为合规；
- 值得沉淀的进知识卡候选（挑战 + 辩驳天然是「面试话术」层素材，接 §5 采集节奏）；
- agent 不自答自结：挑战的判定权在学员，与「验收的判定权是学员的」（§4）同一条边界。
